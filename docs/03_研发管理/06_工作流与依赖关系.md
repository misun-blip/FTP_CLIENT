# 工作流与依赖关系

## 1. 设计原则

6 人协作时，最重要的不是让每个人同时开始写代码，而是让关键路径尽早打通，并尽量减少等待。

本项目采用：

1. 接口先行
2. 协议优先
3. 界面与业务并行
4. 测试前移
5. 分阶段集成

## 2. 六人实际工作流

```text
阶段 0：统一设计
成员 1 + 成员 2 + 成员 5 + 成员 6
        ↓
阶段 1：先打通协议骨架
成员 2 主导，成员 1 配合集成
        ↓
阶段 2：模块并行开发
成员 3 下载
成员 4 上传
成员 5 GUI
成员 6 测试与公共支撑
        ↓
阶段 3：分批联调
先协议 + 下载/上传
再业务 + GUI
最后完整流程
        ↓
阶段 4：回归测试与交付
```

## 3. 成员工作顺序

### 3.1 成员 1：项目统筹与核心集成

先做：

1. 建立工程骨架
2. 明确模块边界
3. 与成员 2 确认核心接口
4. 与成员 5 确认 GUI 需要的数据结构
5. 与成员 6 确认日志、测试和验收方式

随后做：

1. 维护公共模型
2. 接收各模块实现
3. 组织联调
4. 维护 `develop` 和 `main`

### 3.2 成员 2：FTP 协议开发

先做：

1. `connect()`
2. `login()`
3. `send_command()`
4. `list_dir()`
5. 被动模式数据连接

其成果是项目的第一条关键路径，因为成员 3、4、5 都依赖这些能力。

### 3.3 成员 3：下载功能开发

可先并行做：

1. 下载模块类结构
2. 进度回调接口
3. 本地文件写入逻辑
4. 下载续传逻辑草图

依赖成员 2 完成后再做：

1. 真正通过数据连接下载
2. `REST + RETR`
3. 与 GUI 任务区对接

### 3.4 成员 4：上传功能开发

可先并行做：

1. 上传模块类结构
2. 文件分块读取逻辑
3. 进度回调接口
4. 上传续传方案验证

依赖成员 2 完成后再做：

1. 真正通过数据连接上传
2. `STOR`
3. 上传续传实现
4. 与 GUI 任务区对接

### 3.5 成员 5：图形界面开发

可先并行做：

1. 主界面布局
2. 连接区、本地文件区、远程文件区
3. 任务区、日志区
4. 使用 mock 数据完成界面交互

依赖其他模块完成后再做：

1. 接入真实登录结果
2. 接入远程目录数据
3. 接入上传、下载任务
4. 接入日志和异常提示

### 3.6 成员 6：测试、配置与运维支持

从一开始就做：

1. 测试方案
2. 测试用例
3. 日志模块
4. 配置模块
5. 异常分类

随着项目推进继续做：

1. 协议接口测试
2. 上传下载测试
3. 断点续传测试
4. 集成测试
5. 回归测试

## 4. 依赖关系

```text
成员 1 工程骨架
   ├─ 支撑所有人开始开发
   └─ 依赖成员 2、3、4、5、6 的模块完成后进行集成

成员 2 协议层
   ├─ 被成员 3 下载模块依赖
   ├─ 被成员 4 上传模块依赖
   └─ 被成员 5 GUI 真实数据接入依赖

成员 3 下载模块
   └─ 被成员 5 GUI 任务区依赖

成员 4 上传模块
   └─ 被成员 5 GUI 任务区依赖

成员 6 日志、配置、异常
   └─ 被全体成员依赖
```

## 5. 可并行任务与必须串行任务

### 5.1 可并行任务

以下任务可以同时推进：

| 任务 | 负责人 |
|---|---|
| 工程骨架 | 成员 1 |
| FTP 协议基础能力 | 成员 2 |
| 下载模块框架 | 成员 3 |
| 上传模块框架 | 成员 4 |
| GUI 原型与 mock 交互 | 成员 5 |
| 测试方案、日志、配置 | 成员 6 |

### 5.2 必须先后顺序

| 前置任务 | 后续任务 |
|---|---|
| `connect()`、`login()` 完成 | 真实远程目录展示 |
| 数据连接能力完成 | 真正上传、下载 |
| 上传/下载接口确定 | GUI 接入真实任务 |
| 各模块自测通过 | 集成测试 |
| 集成测试通过 | 合并到 `main` |

## 6. 推荐推进节奏

### 第 1 阶段：接口与骨架

| 成员 | 任务 |
|---|---|
| 成员 1 | 工程骨架、公共模型、接口协调 |
| 成员 2 | 连接、登录、目录查询 |
| 成员 3 | 下载模块框架 |
| 成员 4 | 上传模块框架 |
| 成员 5 | GUI 原型 |
| 成员 6 | 测试方案、日志模块、配置模块 |

阶段验收：

- 项目可运行
- 协议层能登录
- GUI 有可运行骨架
- 测试方案和接口文档已存在

### 第 2 阶段：核心功能

| 成员 | 任务 |
|---|---|
| 成员 1 | 组织第一次集成 |
| 成员 2 | 完善数据连接与响应处理 |
| 成员 3 | 完成下载与下载续传 |
| 成员 4 | 完成上传与上传续传 |
| 成员 5 | 接入真实目录、任务、日志 |
| 成员 6 | 执行接口测试，维护缺陷清单 |

阶段验收：

- 上传、下载均可运行
- 目录浏览可用
- GUI 可触发基本任务

### 第 3 阶段：联调与稳定

| 成员 | 任务 |
|---|---|
| 成员 1 | 组织完整流程联调 |
| 成员 2 | 修复协议兼容性问题 |
| 成员 3 | 修复下载续传问题 |
| 成员 4 | 修复上传续传问题 |
| 成员 5 | 优化界面状态反馈 |
| 成员 6 | 执行回归测试与异常测试 |

阶段验收：

- 完整演示流程通过
- 主要异常场景可处理
- 版本可进入 `main`

## 7. 工作流中的关键路径

```text
工程骨架
  ↓
协议层登录与数据连接
  ↓
上传 / 下载真实实现
  ↓
GUI 接入真实业务
  ↓
完整联调与测试
```

其中真正决定项目整体进度的是：

1. 成员 1 是否尽快提供工程骨架
2. 成员 2 是否尽快打通协议基础能力
3. 成员 3、4 是否能在接口稳定后迅速完成核心传输

## 8. 降低等待时间的策略

1. GUI 在真实接口完成前先使用 mock 数据开发
2. 上传、下载在协议层未完成前先完成文件读写和进度逻辑
3. 测试文档和日志模块从第一天就开始
4. 公共模型先定最小版本，后续再扩展
5. 每次联调只接入已经稳定的接口，不一次性压入全部功能

## 9. 推荐日常节奏

| 频率 | 内容 |
|---|---|
| 每日 | 同步当天完成内容、阻塞问题 |
| 每 2 到 3 天 | 合并一次到 `develop` |
| 每周 | 至少一次完整联调 |
| 每个阶段结束 | 输出阶段版本和阶段测试记录 |
