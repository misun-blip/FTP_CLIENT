# 角色与职责

## 1. 分工原则

项目采用 6 人协作开发模式。分工遵循以下原则：

1. 每名成员均负责可独立验收的功能模块
2. 每个核心模块均有明确代码归属
3. 每名成员除开发任务外，还承担一部分文档、测试或联调工作
4. 模块划分尽量减少交叉修改，便于并行开发
5. 最终实验报告能够清楚注明每位成员完成的具体任务与源代码范围

## 3. 分工合理性说明

### 3.1 成员 1：项目统筹与核心集成

该角色不只承担管理工作，还负责公共模型、主程序入口和最终集成，能够保证其在代码层面有明确贡献。由于多个模块最终都需要统一装配，因此由该成员维护：

- 全局工程结构
- 公共数据模型
- 模块装配关系
- 集成版本

### 3.2 成员 2：FTP 协议开发

协议层是上传、下载、目录浏览等功能的基础，技术复杂度高，适合作为独立任务。其工作产出可通过以下内容清晰验收：

- 是否能成功建立控制连接
- 是否能完成登录
- 是否能正确解析服务器响应
- 是否能为列表和文件传输建立数据连接

### 3.3 成员 3 与成员 4：上传、下载分离

上传和下载虽然都属于文件传输，但实现流程、异常场景和续传方式并不相同，拆分为两个角色可以真正并行开发，并减少同一模块内的冲突。

### 3.4 成员 5：图形界面开发

图形界面并非单纯美化，而是承担用户操作入口和状态展示功能，需要与所有业务模块对接，因此单独设置角色较为合理。

### 3.5 成员 6：测试、配置与运维支持

测试与运维并不是“最后补材料”，而是贯穿全程的质量保障工作。该角色应从需求阶段开始参与，先设计测试用例和验收标准，再随开发进度逐步执行单元测试、接口测试、集成测试和回归测试。该角色同时承担 `utils/` 公共支撑模块开发，能够形成明确代码贡献，并提升系统稳定性。

## 9. 调整规则

若后续功能范围发生变化，可根据实际进度微调任务，但应保持以下底线：

1. 每位成员都有明确代码贡献
2. 每个核心功能均有唯一主负责人
3. 公共接口变更后必须同步更新文档
4. 最终报告中的个人任务描述应与实际提交记录保持一致
