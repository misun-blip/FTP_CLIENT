# 协作开发流程规范

## 1. 目的

为保证 6 人小组能够高效、稳定地协同开发，减少重复劳动和代码冲突，统一项目从任务分配、代码开发、测试、联调到版本发布的全过程。

## 2. 适用范围

本规范适用于本项目全部成员，以及以下全部工作内容：

1. 需求确认
2. 任务拆分
3. 接口设计
4. 代码开发
5. 测试
6. 联调
7. 文档维护
8. 版本发布

## 3. 协作基本原则

1. 先设计，后开发
2. 先定接口，后并行实现
3. 每个模块有唯一主负责人
4. 主分支始终保持可运行
5. 小步提交，及时同步
6. 测试前移，不把风险留到最后
7. 文档与代码同步更新

## 4. 角色职责

| 角色 | 主要职责 |
|---|---|
| 项目统筹 | 需求确认、任务拆分、接口统一、版本集成、进度协调 |
| 模块负责人 | 完成本模块设计、开发、自测和文档 |
| 测试负责人 | 设计测试方案、维护测试用例、组织集成测试、跟踪缺陷 |
| 全体成员 | 遵守分支规范、提交规范、评审规范和文档规范 |

## 5. 总体流程

```text
需求确认
  ↓
任务拆分
  ↓
接口设计
  ↓
开发排期
  ↓
模块开发
  ↓
模块自测
  ↓
代码评审
  ↓
合并到 develop
  ↓
集成测试
  ↓
阶段联调
  ↓
稳定版本发布到 main
```

## 6. 任务管理流程

### 6.1 任务创建

每个任务必须包含：

- 任务名称
- 任务目标
- 负责人
- 依赖项
- 截止时间
- 验收标准

### 6.2 任务分类

| 类型 | 示例 |
|---|---|
| 功能任务 | 登录、上传、下载 |
| 缺陷任务 | 修复续传失败 |
| 文档任务 | 更新接口说明 |
| 测试任务 | 编写下载测试 |
| 集成任务 | 接入真实协议层 |

### 6.3 任务状态

```text
todo
in_progress
blocked
review
done
```

### 6.4 任务完成标准

一个任务只有同时满足以下条件，才能视为完成：

1. 代码已实现
2. 自测已完成
3. 文档已更新
4. 已提交代码
5. 已通过评审或验收

## 7. 接口管理流程

### 7.1 接口先行

在多个模块存在依赖时，必须先确定：

1. 函数名
2. 参数
3. 返回值
4. 异常形式
5. 调用顺序

### 7.2 接口冻结

进入开发阶段后，基础接口原则上不再随意修改。

若必须修改，流程如下：

```text
提出变更
  ↓
评估影响
  ↓
更新接口文档
  ↓
通知受影响成员
  ↓
修改实现与调用方
  ↓
重新测试
```

### 7.3 接口文档要求

每个公共接口必须说明：

- 功能
- 参数
- 返回值
- 可能异常
- 调用示例

## 8. Git 分支规范

### 8.1 分支结构

```text
main
develop
feature/*
fix/*
docs/*
```

### 8.2 分支用途

| 分支 | 用途 |
|---|---|
| `main` | 稳定、可演示版本 |
| `develop` | 日常集成分支 |
| `feature/*` | 功能开发 |
| `fix/*` | 缺陷修复 |
| `docs/*` | 文档更新 |

### 8.3 开发规则

1. 不直接在 `main` 上开发
2. 功能开发从 `develop` 拉分支
3. 一个分支只处理一类问题
4. 功能完成后先合并到 `develop`
5. `develop` 通过测试后，再合并到 `main`

## 9. 代码提交规范

### 9.1 提交粒度

一次提交应尽量只做一件事。

### 9.2 提交格式

```text
feat: add login flow
fix: handle interrupted download
docs: update interface baseline
test: add upload resume cases
refactor: split transfer helpers
```

### 9.3 提交前检查

- [ ] 代码可运行
- [ ] 自测通过
- [ ] 没有无关文件
- [ ] 文档同步更新
- [ ] 提交信息清晰

## 10. 开发流程

### 10.1 开发前

1. 阅读任务说明
2. 确认接口基线
3. 确认依赖是否满足
4. 从 `develop` 创建个人功能分支

### 10.2 开发中

1. 优先完成最小可运行版本
2. 每天至少同步一次最新代码
3. 发现接口问题立即反馈
4. 避免长期修改他人模块

### 10.3 开发完成后

1. 完成自测
2. 补充或更新测试用例
3. 更新对应文档
4. 提交代码
5. 发起评审

## 11. 代码评审流程

### 11.1 评审要求

任何准备合并到 `develop` 的代码，至少需经过 1 名其他成员查看。

### 11.2 评审重点

1. 是否符合接口约定
2. 是否破坏现有功能
3. 是否存在明显异常风险
4. 是否补充测试
5. 是否同步更新文档

### 11.3 评审结果

| 结果 | 处理方式 |
|---|---|
| 通过 | 可合并 |
| 需修改 | 修改后再次提交 |
| 暂缓 | 先解决依赖或设计问题 |

## 12. 测试流程

### 12.1 测试前移

测试不等到项目结束才开始，而是贯穿全过程。

### 12.2 测试层级

| 阶段 | 测试内容 |
|---|---|
| 模块开发阶段 | 单元测试、自测 |
| 模块接入阶段 | 接口测试 |
| 多模块联动阶段 | 集成测试 |
| 交付前 | 回归测试、异常测试 |

### 12.3 缺陷流转

```text
发现缺陷
  ↓
记录缺陷
  ↓
分配责任人
  ↓
修复
  ↓
复测
  ↓
关闭
```

## 13. 联调流程

### 13.1 联调原则

联调应分阶段推进，不应等到最后一次性集成。

### 13.2 联调阶段

| 阶段 | 内容 |
|---|---|
| 第一次联调 | 应用骨架 + 协议层 |
| 第二次联调 | 协议层 + 上传/下载 |
| 第三次联调 | 业务层 + GUI |
| 最终联调 | 完整流程 + 异常场景 |

### 13.3 联调前置条件

- [ ] 模块已自测
- [ ] 公共接口已实现
- [ ] 已知问题已记录
- [ ] 必要文档已更新

## 14. 文档管理规范

### 14.1 文档要求

代码变化若影响以下内容，必须同步更新文档：

- 接口
- 数据结构
- 业务流程
- 测试用例
- 运维方式

### 14.2 文档分类

| 分类 | 内容 |
|---|---|
| 总体设计 | 需求、架构、模块 |
| 详细设计与接口 | 数据结构、接口、流程 |
| 研发管理 | 分工、计划、协作、版本 |
| 测试与运维 | 测试、运行、交付 |

## 15. 发布流程

### 15.1 阶段版本

| 版本 | 内容 |
|---|---|
| v0.1 | 骨架、登录 |
| v0.2 | 目录浏览 |
| v0.3 | 上传、下载 |
| v0.4 | 断点续传 |
| v0.5 | GUI 联调 |
| v1.0 | 最终提交版本 |

### 15.2 发布前检查

- [ ] 功能完成
- [ ] 测试通过
- [ ] 文档更新
- [ ] 主流程可演示
- [ ] 已知严重缺陷清零

### 15.3 发布规则

只有 `develop` 经过测试并达到阶段验收标准后，才能合并到 `main`。

## 16. 冲突处理规范

### 16.1 冲突预防

1. 模块划分清晰
2. 公共文件少人修改
3. 接口变更提前同步
4. 经常拉取最新代码

### 16.2 冲突出现后

1. 先确认接口文档
2. 由相关模块负责人沟通
3. 必要时由项目统筹裁定
4. 解决后重新执行测试

## 17. 日常协作节奏

| 周期 | 内容 |
|---|---|
| 每日 | 简短同步：已完成、今日计划、阻塞 |
| 每 2 到 3 天 | 合并一次到 `develop` |
| 每周 | 至少一次联调 |
| 每阶段结束 | 输出阶段版本和测试记录 |

## 18. 最终验收标准

1. 各模块均有明确负责人和源代码归属
2. 主流程可稳定运行
3. 上传、下载、断点续传通过测试
4. 文档齐全
5. 版本可在 Windows 平台正常运行
